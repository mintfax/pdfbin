# pdfbin.net design

**Status:** Draft - brainstorming output, pending implementation plan.
**Date:** 2026-05-12.
**Origin:** Parked from mintfax issue #172 ("Blue-sky: developer sandbox experience"), session 1. Lifted out of the mintfax sandbox scope on the call that pdfbin should be a standalone public utility, not an artifact of `test.mintfax.com`.

## One-line description

pdfbin.net is a free library of test PDFs at stable URLs you can drop straight into your test suite. Each fixture is a PDF that does one specific thing - it's clean, or it's corrupt in a known way, or it's encrypted with a documented password, or it's huge, or it's a scan, or it's a form. The idea is that anyone writing code that touches PDFs - parsers, viewers, OCR pipelines, fax services, document-conversion services - has something real to point at when they want to know how their code behaves on the awkward cases.

Under the hood: fixtures are generated by committed Python scripts (so the corruption is auditable, not mystery bytes), URLs are immutable (the bytes at `/corrupt/xref-truncated.pdf` today are the same bytes there next year), and everything is CC0.

## Why this exists

Today the practice for "I need a sample PDF for my test suite" is:
- find a PDF on GitHub
- right-click save into the repo
- pray it stays addressable

Research into prior art (see "Prior art" below) found one meaningful incumbent (samplefile.com - 21 fixtures with a JSON manifest) and a thicket of unmaintained or non-fixture-positioned sites. No existing site combines (a) explicit CC0 licensing, (b) immutable URLs you can hard-code in CI, (c) a corruption taxonomy that actually exercises parser failure modes, and (d) a machine-readable catalog. That four-way combination is pdfbin's slot.

The mintfax sandbox is the first known consumer, but the design deliberately doesn't depend on mintfax in any way - pdfbin is independently useful to PDF.js, pypdf, ocrmypdf, pdf-lib, ghostscript users, fax APIs, document converters, and security-fuzzing pipelines.

## Scope

**In v1:**
- 8 fixture categories: clean, corrupt, encrypted, large, pdfa, scanned, forms, pages
- ~48 fixtures total
- Hugo static site on GitHub Pages with the family two-branch flow (dev / production)
- Caddy dev preview at `pdfbin.example.dev`
- Python generation pipeline using pikepdf, reportlab, img2pdf, Pillow, and Ghostscript shell-out
- Discoverability surfaces: HTML index, `/catalog.json`, `/llms.txt`, `/openapi.json`
- CC0-1.0 license for all fixtures; MIT for site code
- Landing page designed externally (claude.ai/design prompt included)

**Out of v1 (candidates for later):**
- XFA forms (separate beast from AcroForm)
- JBIG2 images, exotic/missing fonts, CMYK-only image streams, brotli streams
- A `/random/{seed}/{pages}.pdf` procedural endpoint for long-tail junk PDFs
- Self-hosted Docker image (`docker run pdfbin/pdfbin`) for hermetic CI
- HEAD endpoint returning sha256 in a custom header
- Migration to Cloudflare R2 if/when GH Pages bandwidth or file-size limits start to bite
- In-CI PDF/A validation (would require a non-Java validator we trust)

**Pre-flight blocker:** `pdfbin.net` was unregistered as of the mintfax session that produced this design. The domain has to be registered before any code lands; the whole design rests on the name being available and held by the project.

## Architecture

Hugo static site. Dev branch is where work happens; pushing to `production` triggers GitHub Pages to build and publish. Family two-branch flow, same as mintfax-site.

Caddy serves the local `public/` build at `https://pdfbin.example.dev` so dev previews work without running `hugo server` (family convention: a one-shot `hugo --minify` and a refresh, per the mintfax-site working rules).

A Python generation pipeline lives in `generate/`. It reads a small set of hand-curated source PDFs and produces every fixture under `static/`. Generated outputs are committed to the repo so the Hugo build is a no-op static serve. The pipeline is idempotent; CI re-runs it and fails if `git diff --exit-code static/` shows drift.

The split between `generate/` and `static/` is load-bearing: `generate/` is the audit trail for *why* a fixture is what it is; `static/` is the deployment surface. A reviewer can read `generate/builders/corrupt.py` and see that `xref-truncated.pdf` literally means "byte-truncated at the offset where the xref table starts", rather than hand-mangled mystery bytes.

## URL grammar and filename conventions

Two-segment path: `pdfbin.net/<category>/<filename>.pdf`.

No version prefix in the path. Filenames are immutable - if a fixture's semantics need to change, a new filename ships and the old one stays. The `catalog.json` document is the only thing that gets versioned (via a top-level `schema_version` field).

Filenames within a category are hyphen-separated lowercase, leading dimension first. Concretely:

```
/clean/a4-1page.pdf
/clean/jis-b5-1page.pdf
/clean/a4-1page-100kb.pdf
/corrupt/xref-truncated.pdf
/encrypted/aes256-owner.pdf
/large/10mb.pdf
/pdfa/3b-with-attachment.pdf
/scanned/skewed-3deg.pdf
/forms/empty-acroform.pdf
/pages/mixed-orientation.pdf
```

Top-level discovery URLs:

```
/                  HTML index
/catalog.json      machine catalog
/llms.txt          AI-agent summary
/openapi.json      OpenAPI 3.1 spec
/robots.txt        permissive
```

## v1 fixture catalog

Three paper-size families are represented in `/clean/` (DIN A4, US Letter, JIS B5). JIS B5 is explicitly *not* ISO B5 - the dimensions differ (182×257mm vs 176×250mm) and that distinction trips up code assuming a single B-series. Each fixture's catalog entry carries an explicit `paper_size` property.

## catalog.json schema

Single JSON document at `/catalog.json`. Top-level wraps a `fixtures` array. Schema is versioned via `schema_version` (semver). Fixture identities (path) are stable forever.

```json
{
  "schema_version": "1.0.0",
  "site": "pdfbin.net",
  "license_default": "CC0-1.0",
  "generated_at": "2026-05-12T14:48:00Z",
  "fixture_count": 48,
  "categories": [
    "clean", "corrupt", "encrypted", "large",
    "pdfa", "scanned", "forms", "pages"
  ],
  "fixtures": [
    {
      "path": "/corrupt/xref-truncated.pdf",
      "url": "https://pdfbin.net/corrupt/xref-truncated.pdf",
      "category": "corrupt",
      "name": "xref-truncated",
      "description": "PDF byte-truncated at the start of the xref table. Parsers that don't fall back to xref-recovery will fail to read it.",
      "license": "CC0-1.0",
      "size_bytes": 12345,
      "sha256": "abcd...ef01",
      "pdf_version": "1.7",
      "page_count": 3,
      "tags": ["corruption", "xref", "truncated"],
      "properties": {
        "encrypted": false,
        "linearized": false,
        "expected_failure": "xref-recovery-required"
      },
      "source_script": "generate/builders/corrupt.py:xref_truncated"
    }
  ]
}
```

Category-specific `properties` keys:

```
clean:     paper_size ("DIN-A4" | "US-Letter" | "JIS-B5"), dimensions_mm
encrypted: encryption_algorithm, owner_password, user_password
pdfa:      pdfa_conformance ("1B" | "1A" | "2B" | "3B" | "4"),
           validation ("ghostscript-strict, no veraPDF cross-check")
forms:     has_acroform, is_signed, field_count
scanned:   dpi, noise_level, skew_degrees
large:     intent ("bytes" | "pages")
corrupt:   expected_failure (short token describing what should fail)
```

`source_script` is the audit-trail link: every fixture is regenerable from a named Python function. That's what samplefile.com can't claim and what makes the corruption taxonomy trustworthy in adversarial review.

## Discoverability surfaces

Four surfaces, generated from the same builder manifest:

### `/` - HTML index

Hugo template rendering the catalog grouped by category, with copy-paste URLs and per-fixture descriptions. Design is delegated to claude.ai/design (prompt at the bottom of this doc).

### `/catalog.json`

As above. Primary machine surface. CI suites pin by `path` (stable) and verify by `sha256` (also stable, but rotates if the bytes change - they don't, per the immutability contract, but verifying it costs nothing).

### `/llms.txt`

llmstxt.org-style markdown summary. Concrete v1 content:

```markdown
# pdfbin.net

A free CC0 library of PDF fixtures for testing. Each fixture is a PDF at a
stable URL designed to exercise one specific behavior - clean, corrupt in a
known way, encrypted, large, PDF/A conformant, scanned, form-bearing, or
having a particular page count.

## Discovery

- /catalog.json - machine catalog: path, sha256, page_count, pdf_version,
  properties, license per fixture
- /openapi.json - OpenAPI 3.1 spec with every fixture as a GET endpoint

## Categories

- /clean/      canonical happy-path PDFs (DIN, US, JIS paper sizes)
- /corrupt/    deterministically damaged PDFs (xref-truncated, ...)
- /encrypted/  documented owner/user passwords ("ownerpass", "userpass")
- /large/      bytes-sized fixtures up to 50MB
- /pdfa/       conformance variants 1B, 1A, 2B, 3B, 4
- /scanned/    scan-quality variants for OCR
- /forms/      AcroForm states (empty/partial/filled/signed)
- /pages/      page-count, orientation, and paper-size variants

## Stability

URLs are immutable. If a fixture's semantics change, a new filename ships
and the old one stays. Pin by sha256 from catalog.json for byte-exact CI.

## License

All fixtures CC0-1.0. Site code MIT. Source: github.com/example/pdfbin
```

### `/openapi.json`

OpenAPI 3.1, generated from the builder manifest. One path per fixture; each is a GET returning `application/pdf`. Sketch:

```yaml
openapi: 3.1.0
info:
  title: pdfbin.net
  version: "1.0.0"
  description: Free CC0 PDF fixtures at stable URLs
  license: { name: CC0-1.0, identifier: CC0-1.0 }
servers: [{ url: https://pdfbin.net }]
paths:
  /corrupt/xref-truncated.pdf:
    get:
      summary: PDF truncated at xref table start
      tags: [corrupt]
      responses:
        "200":
          description: PDF fixture (CC0)
          content: { application/pdf: { schema: { type: string, format: binary } } }
  # ... one entry per fixture
```

## Library and tooling stack

Python pipeline, no Java.

- **pikepdf** (qpdf C binding) - read/write/encrypt workhorse. Handles AES-256, AES-128, RC4-128, RC4-40 cleanly.
- **reportlab** - generate fresh clean PDFs targeted at specific page counts, byte sizes, and PDF spec versions.
- **Ghostscript** shell-out with `-dPDFA -dPDFACompatibilityPolicy=1` (strict mode: abort on non-conformance, do not silently degrade) - PDF/A generation. We trust Ghostscript's strict-mode output; no separate validator runs in CI.
- **img2pdf** - assemble scanned-image PDFs.
- **Pillow** - synthesize the scan images (noise, skew, dpi variants).
- **pypdf** - light raw-byte work for the `/corrupt/` builders (locating xref offsets, trailer boundaries, etc., before mutating).

System dependencies (installed in the CI Dockerfile):

- `qpdf` (for pikepdf)
- `ghostscript`

Explicitly not used: veraPDF (Java). The tradeoff is no in-CI PDF/A validation; `/pdfa/` fixtures are only as conformant as Ghostscript's strict mode produces. Catalog metadata states this explicitly in each PDF/A fixture's `validation` property. Consumers wanting harder verification can run veraPDF locally against the published bytes; we're not putting JVM in our build.

## Generation pipeline

`generate/pipeline.py` is the single entry point:

```python
from builders import clean, corrupt, encrypted, large, pdfa, scanned, forms, pages
from catalog import emit_catalog, emit_llms_txt, emit_openapi

manifests = []
for module in [clean, corrupt, encrypted, large, pdfa, scanned, forms, pages]:
    manifests.extend(module.build_all())

emit_catalog(manifests)    # static/catalog.json
emit_llms_txt(manifests)   # static/llms.txt
emit_openapi(manifests)    # static/openapi.json
```

Each builder is a pure function: input is one or more files in `generate/sources/`, output is a written PDF in `static/<category>/` plus a returned metadata dict. The catalog emitter aggregates the dicts.

CI is a GitHub Action that:

1. Builds a Docker image with `qpdf`, `ghostscript`, and the Python deps.
2. Runs `python generate/pipeline.py`.
3. Runs `git diff --exit-code static/`. If anything changed, the action fails - forcing the contributor to regenerate locally and commit.

This is how `static/` stays a true snapshot of `generate/` without the build needing to push anything back into the repo.

## Hosting and deployment

GitHub Pages, family two-branch flow:

- `dev` is the default branch. All work happens here.
- Pushing to `production` triggers the Pages workflow, which builds with Hugo and deploys.
- Caddy serves the local `public/` build at `https://pdfbin.example.dev` for dev previews.

Tradeoff accepted: GH Pages enforces a 100MB per-file ceiling, a ~1GB repo size ceiling, and 100GB/month bandwidth. Hence `/large/` caps at 50MB per file (with headroom). If pdfbin becomes popular enough to threaten the bandwidth ceiling, the migration target is Cloudflare Pages + R2; that migration is explicitly out of scope for v1.

`CLAUDE.md` will codify the family working rules: commit and push after every change; do not run `hugo server`; use one-shot `hugo --minify` and Caddy for previews.

## Open items and followups

- **Domain registration.** Pre-flight blocker. Confirm `pdfbin.net` is still available; register; configure DNS for GitHub Pages + Cloudflare-or-equivalent later if needed.
- **GitHub org/repo path.** Assumed `github.com/example/pdfbin`; confirm with the family naming convention.
- **Source-asset provenance.** The hand-curated PDFs in `generate/sources/` need to be either generated by us or imported from explicitly CC0-licensed sources. Document the chain of custody in `generate/sources/PROVENANCE.md`.
- **Mintfax sandbox wiring.** Mintfax issue #172 expects pdfbin to be the fixture host its document-URL scenarios point to. That wiring is mintfax's concern, not pdfbin's, but the catalog's `/corrupt/` and `/encrypted/` URLs should be considered "API surface" mintfax depends on.

## Prior art (research summary)

Findings from research that informed this design:

- **Bin family** (httpbin, webhook.site, pastebin, hastebin, mockbin): split between *ephemeral capture* (webhook.site, RequestBin - random IDs, user-generated) and *curated catalog* (httpbin, hastebin - stable pronounceable paths, single-tenant). pdfbin sits firmly in the curated half.
- **Placeholder/fixture family** (picsum.photos, placehold.co, jsonplaceholder, fakerapi, robohash): path-based parameters, not query strings. Lorem Picsum's `/v2/list` machine index is the discoverability gold standard - and nobody else in the family ships one. via.placeholder.com died in March 2026 when the domain was sold; the longevity story is part of the product. Sites that omit licensing create real CI adoption friction.
- **PDF prior art:** samplefile.com is the meaningful incumbent (21 curated fixtures, JSON manifest with SHA256s) but lacks explicit CC0, immutable URLs, and a corruption taxonomy. ArturT/Test-PDF-Files is the closest "casual CI fixture" set - 3 files, abandoned at 3 commits. py-pdf/sample-files, mozilla/pdf.js, and veraPDF/veraPDF-corpus are each excellent in their niche but none positioned as a general developer-facing fixture host with stable URLs and CC0 licensing.

The unique slot for pdfbin.net is the combination: CC0 + immutable URLs + corruption taxonomy + machine-readable catalog. Without all four, this would be a samplefile.com clone.
