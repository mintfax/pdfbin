# pdfbin.net design

**Status:** Draft - brainstorming output, pending implementation plan.
**Date:** 2026-05-12.
**Origin:** Parked from mintfax issue #172 ("Blue-sky: developer sandbox experience"), session 1. Lifted out of the mintfax sandbox scope on the call that pdfbin should be a standalone public utility, not an artifact of `test.mintfax.com`.

## One-line description

pdfbin.net is a free library of test PDFs at stable URLs you can drop straight into your test suite. Each fixture is a PDF that does one specific thing - it's clean, or it's corrupt in a known way, or it's encrypted with a documented password, or it's huge, or it's a scan, or it's a form, or it's shaped like a real-world document (fax cover, invoice, IRS 1040, lab report, ...). The idea is that anyone writing code that touches PDFs - parsers, viewers, OCR pipelines, fax services, document-conversion services - has something real to point at when they want to know how their code behaves on the awkward cases.

Under the hood: fixtures are generated by committed Python scripts (so corruption is auditable, not mystery bytes), URLs are flat and immutable (the bytes at `/xref-truncated.pdf` today are the same bytes there next year), every fixture is described by a typed facet record in `catalog.json`, and everything is CC0.

## Why this exists

The practice for "I need a sample PDF for my test suite" today is: find a PDF on GitHub, right-click save into the repo, pray it stays addressable.

Research into prior art (see "Prior art" at the end of this doc) found one meaningful incumbent (samplefile.com - 21 fixtures with a JSON manifest) and a thicket of unmaintained or non-fixture-positioned sites. No existing site combines (a) explicit CC0 licensing, (b) flat immutable URLs you can hard-code in CI, (c) a corruption taxonomy that actually exercises parser failure modes, (d) realistic document shapes (fax cover, invoice, IRS form), and (e) a typed multi-axis catalog. That five-way combination is pdfbin's slot.

The mintfax sandbox is the first known consumer (its document-side scenarios will point at pdfbin URLs), but the design deliberately doesn't depend on mintfax in any way - pdfbin is independently useful to PDF.js, pypdf, ocrmypdf, pdf-lib, ghostscript users, fax APIs, document converters, and security-fuzzing pipelines.

## The structural call: flat URLs, facets in the catalog

The most consequential design decision in this spec is what *isn't* in the URL.

The natural first instinct (and what an earlier draft of this design did) is to carve fixtures into top-level categories: `/clean/`, `/corrupt/`, `/encrypted/`, `/scanned/`, and so on. That structure is wrong for pdfbin, for a reason worth being explicit about: **most fixtures have multiple notable attributes**, and a category URL forces an arbitrary "primary" choice. A scanned fax cover sheet is scanned *and* a fax cover *and* letter-sized *and* one-page; filing it under `/scanned/` demotes the other three attributes to metadata-only and makes the cross-axis query ("noisy scanned receipts") impossible from the URL space. The "categories" we'd be tempted to use are also not apples-to-apples - they mix health states (clean/corrupt), access states (encrypted), spec compliance (PDF/A), provenance (scanned), feature usage (forms), and form factor (page count) into a single namespace by accident.

The alternative this spec adopts: **URLs are flat, identity-only. Every notable attribute lives in a typed facet record in `catalog.json`. The HTML index renders multiple views of the same data at build time.**

```
/<id>.pdf            canonical fixture URL (flat)
/catalog.json        machine catalog with typed facets per fixture
/openapi.json        OpenAPI 3.1 spec
/llms.txt            AI-agent summary
/robots.txt
/                    HTML index with multiple "By <axis>" sections
/by-fault.html       focused single-view page
/by-document.html
/by-provenance.html
/by-spec.html
/by-form-factor.html
```

The flat structure matches the bin/placeholder family (`placehold.co/600x400.png`, `pastebin.com/<id>`, `picsum.photos/200/300`) rather than the REST-resource-collection family. The `.pdf` extension does the disambiguation work against the discovery surfaces.

This unlocks three things the category structure couldn't:

1. **Multi-attribute fixtures are natural.** A scanned fax cover sheet is one fixture with multiple facet values - it appears under both "By Document Shape: fax-cover-sheet" and "By Provenance: scanned" in the HTML index, without duplication.
2. **New axes are catalog schema changes, not URL contract breaks.** If we want to add `color_profile`, `language`, or `pdf_generator` axes later, we extend the facet schema; existing URLs don't move.
3. **Versioning collapses into catalog metadata** (see "Versioning" below).

## Versioning

Three orthogonal versioning surfaces, each with its own lifecycle:

| What's being versioned   | Where it's versioned                 | Breakage contract |
|--------------------------|--------------------------------------|-------------------|
| Fixture identity (bytes) | The URL is the version - immutable   | Never breaks. New variant = new ID. |
| Fixture lifecycle        | `status` + `superseded_by` in catalog| Old fixtures stay servable; new ones recommended. |
| Catalog document schema  | top-level `schema_version` (semver)  | Major bumps allowed; consumers can pin. |

The bytes at `/<id>.pdf` never change. If a fixture turns out to be wrong or misleading, we ship a new ID and mark the old one `"status": "deprecated"` with a `"superseded_by": "<new-id>"` pointer. Nothing is ever deleted; URLs are forever.

The rejected alternative (path-prefix versioning like `/v1/<id>.pdf`) would force every fixture to be versioned together even when most never need to change, and would make consumers commit to a prefix in their CI suites. Flat URLs with catalog lifecycle fields let individual fixtures evolve independently.

## Scope

**In v1:**
- ~52 fixtures spanning health, access, spec, form-factor, size, feature, provenance, and document-shape axes
- Hugo static site on GitHub Pages with the family two-branch flow (dev / production)
- Caddy dev preview at `pdfbin.example.dev`
- Python generation pipeline using pikepdf, reportlab, img2pdf, Pillow, and Ghostscript shell-out
- Discoverability surfaces: HTML index (multi-view), `/catalog.json`, `/llms.txt`, `/openapi.json`
- CC0-1.0 license for all fixtures; MIT for site code
- Landing page designed externally (claude.ai/design prompt at the bottom of this doc)

**Out of v1 (candidates for later):**
- XFA forms (separate beast from AcroForm)
- JBIG2 images, exotic/missing fonts, CMYK-only image streams, brotli streams
- A `/random-<seed>-<pages>.pdf` procedural endpoint for long-tail junk PDFs
- Self-hosted Docker image (`docker run pdfbin/pdfbin`) for hermetic CI
- HEAD endpoint returning sha256 in a custom header
- Migration to Cloudflare R2 if/when GH Pages bandwidth or file-size limits start to bite
- In-CI PDF/A validation (would need a non-Java validator we trust)
- Additional facet axes: `color_profile`, `language`, `pdf_generator`

**Pre-flight blocker:** `pdfbin.net` was unregistered as of the mintfax session that produced this design. The domain has to be registered before any code lands.

## Architecture

Hugo static site. Dev branch is where work happens; pushing to `production` triggers GitHub Pages to build and publish. Family two-branch flow, same as mintfax-site.

Caddy serves the local `public/` build at `https://pdfbin.example.dev` so dev previews work without running `hugo server` (family convention: one-shot `hugo --minify` and refresh, per the mintfax-site working rules).

A Python generation pipeline lives in `generate/`. It reads a small set of hand-curated source PDFs and produces every fixture under `static/`. Generated outputs are committed to the repo so the Hugo build is a no-op static serve. The pipeline is idempotent; CI re-runs it and fails if `git diff --exit-code static/` shows drift.

The split between `generate/` and `static/` is load-bearing. `generate/` is the audit trail; `static/` is the deployment surface. A reviewer can read `generate/builders/health.py` and see that `xref-truncated.pdf` literally means "byte-truncated at the offset where the xref table starts", not hand-mangled mystery bytes.

Builders are organized by the facet axis they primarily vary, not by the old top-level categories. A builder can emit fixtures with multiple facet values (e.g., `documents.py` emits both `fax-cover-letter-clean` and `fax-cover-letter-scanned-noisy`).

## Fixture IDs and URL grammar

URLs are `pdfbin.net/<id>.pdf`. No category prefix, no version prefix.

The `<id>` is a hyphen-separated lowercase slug that encodes enough of the fixture's distinctive facets to be self-explanatory in a code review. The ID is the immutable contract; the catalog facets are the authoritative metadata.

Conventions for ID composition:

- **Identity-defining facet leads** - whichever facet most defines this fixture goes first. `xref-truncated` (health), `aes256-owner` (access), `fax-cover` (document_shape), `pdfa-3b` (spec).
- **Disambiguating facets follow as needed** - paper size, page count, scan quality - only include what's needed for uniqueness within the catalog.
- **No numbered suffixes** - if two fixtures would collide, expand one of their IDs with the distinguishing facet. `clean-a4-1page` vs `clean-letter-1page` not `clean-1page` vs `clean-1page-v2`.

## Facets

Every fixture has a typed facet record. Each axis has a controlled vocabulary documented in `generate/facets.py`. Adding a new value to an axis is a deliberate change to that file (not a value snuck into a builder somewhere).

| Axis             | Type       | Values                                                                              |
|------------------|------------|-------------------------------------------------------------------------------------|
| `health`         | enum       | `valid` \| `corrupt-xref-truncated` \| `corrupt-header-truncated` \| `corrupt-stream-length-mismatch` \| `corrupt-object-generation-mismatch` \| `corrupt-trailer-missing` \| `corrupt-eof-missing` \| `corrupt-byte-flipped` |
| `access`         | enum       | `open` \| `encrypted-aes256-owner` \| `encrypted-aes256-user` \| `encrypted-aes256-both` \| `encrypted-aes128-owner` \| `encrypted-aes128-user` \| `encrypted-rc4-128-owner` \| `encrypted-rc4-40-owner` |
| `document_shape` | enum       | `blank` \| `fax-cover-sheet` \| `invoice` \| `receipt` \| `irs-1040` \| `bank-statement` \| `contract-nda` \| `lab-report`                |
| `provenance`     | enum       | `digital-native` \| `scanned-clean` \| `scanned-noisy` \| `scanned-skewed` \| `scanned-noisy-skewed` |
| `paper_size`     | enum       | `DIN-A4` \| `US-Letter` \| `JIS-B5` \| `mixed`                                       |
| `page_count`     | int        | exact count                                                                          |
| `orientation`    | enum       | `portrait` \| `landscape` \| `mixed`                                                |
| `spec`           | enum       | `PDF-1.4` \| `PDF-1.7` \| `PDF-2.0` \| `PDF/A-1B` \| `PDF/A-1A` \| `PDF/A-2B` \| `PDF/A-3B` \| `PDF/A-4` |
| `features`       | set\<enum> | subset of `{acroform, signed, embedded-file}`                                       |
| `scan_quality`   | optional   | `{dpi: int, noise: "low"\|"high", skew_degrees: int}` - present when provenance starts with `scanned-` |
| `passwords`      | optional   | `{owner: string \| null, user: string \| null}` - present when access starts with `encrypted-` |

Canonical encryption passwords across all `/encrypted-*` fixtures: `owner="ownerpass"`, `user="userpass"`. Stated in the facet record for each encrypted fixture and re-stated in `llms.txt`.

## catalog.json schema

Single JSON document at `/catalog.json`. Top-level wraps a `fixtures` array. Schema is versioned via `schema_version` (semver). Fixture identities (id) are stable forever.

```json
{
  "schema_version": "1.0.0",
  "site": "pdfbin.net",
  "license_default": "CC0-1.0",
  "generated_at": "2026-05-12T14:48:00Z",
  "fixture_count": 52,
  "facet_axes": {
    "health":         ["valid", "corrupt-xref-truncated", "..."],
    "access":         ["open", "encrypted-aes256-owner", "..."],
    "document_shape": ["blank", "fax-cover-sheet", "invoice", "..."],
    "provenance":     ["digital-native", "scanned-clean", "..."],
    "paper_size":     ["DIN-A4", "US-Letter", "JIS-B5", "mixed"],
    "spec":           ["PDF-1.4", "PDF-1.7", "PDF-2.0", "PDF/A-1B", "..."]
  },
  "fixtures": [
    {
      "id": "fax-cover-letter-scanned-noisy",
      "url": "https://pdfbin.net/fax-cover-letter-scanned-noisy.pdf",
      "added": "2026-05-12",
      "status": "current",
      "superseded_by": null,
      "license": "CC0-1.0",
      "size_bytes": 487123,
      "sha256": "abcd...ef01",
      "page_count": 1,
      "description": "Fax cover sheet on US Letter, rendered as a noisy 300 DPI scan. Useful for OCR test suites that need a realistic faxed document.",
      "facets": {
        "health":         "valid",
        "access":         "open",
        "document_shape": "fax-cover-sheet",
        "provenance":     "scanned-noisy",
        "paper_size":     "US-Letter",
        "orientation":    "portrait",
        "spec":           "PDF-1.7",
        "features":       [],
        "scan_quality":   { "dpi": 300, "noise": "high", "skew_degrees": 0 }
      },
      "source_script": "generate/builders/documents.py:fax_cover_scanned_noisy"
    }
  ]
}
```

`facet_axes` at the top of the document declares the controlled vocabulary for the major enum axes so consumers can validate without re-deriving from `generate/facets.py`. If we add a new value or a new axis, both the schema_version and `facet_axes` reflect it.

`source_script` is the audit-trail link: every fixture is regenerable from a named Python function. That's what samplefile.com can't claim and what makes the corruption taxonomy trustworthy in adversarial review.

## Discoverability surfaces

Four surfaces, all generated from the same builder manifest. All static. No runtime computation.

### `/` and per-view HTML pages

Hugo reads `catalog.json` at build time and renders:

- `/` - the multi-view home: one long page, httpbin-style. Sections in order: By Failure Mode, By Document Shape, By Provenance, By Spec, By Form Factor. Each section lists every fixture relevant to that axis with its ID, one-line description, and full URL.
- `/by-fault.html`, `/by-document.html`, `/by-provenance.html`, `/by-spec.html`, `/by-form-factor.html` - focused single-view pages for SEO and direct linking.

A fixture with multiple notable facet values appears in multiple sections of `/` and multiple per-view pages. The data is one source (catalog.json); the presentation is the multi-view.

Design is delegated to claude.ai/design (prompt at the bottom of this doc).

### `/catalog.json`

The primary machine surface. CI suites pin by `id` (stable forever) and can verify by `sha256` (also stable). All facet axes available for client-side filtering.

### `/llms.txt`

llmstxt.org-style markdown summary. Concrete v1 content:

```markdown
# pdfbin.net

A free CC0 library of PDF fixtures for testing. Each fixture is a PDF at a
stable flat URL designed to exercise one or more specific behaviors -
clean, corrupt in a known way, encrypted, large, PDF/A conformant,
scanned, form-bearing, shaped like a real document (fax cover, invoice,
IRS 1040, ...), or any combination.

## URL contract

Every fixture lives at https://pdfbin.net/<id>.pdf. Bytes are immutable;
the URL is the version. If a fixture is wrong, a new ID ships and the old
one stays available, marked status: deprecated.

## Discovery

- /catalog.json - typed catalog: every fixture's facets, sha256,
  page_count, license, lifecycle (added/status/superseded_by)
- /openapi.json - OpenAPI 3.1 spec with every fixture as a GET endpoint

## Facet axes

- health         valid / corrupt-{xref-truncated, header-truncated, ...}
- access         open / encrypted-{aes256-owner, aes128-user, ...}
- document_shape blank / fax-cover-sheet / invoice / receipt / irs-1040 /
                 bank-statement / contract-nda / lab-report
- provenance     digital-native / scanned-{clean, noisy, skewed, ...}
- paper_size     DIN-A4 / US-Letter / JIS-B5 / mixed
- spec           PDF-1.4 / PDF-1.7 / PDF-2.0 / PDF/A-1B ... PDF/A-4
- features       acroform / signed / embedded-file

## Conventions

Encrypted PDFs use owner="ownerpass", user="userpass" unless an encrypted
fixture's catalog entry says otherwise.

## License

All fixtures CC0-1.0. Site code MIT. Source: github.com/mintfax/pdfbin
```

### `/openapi.json`

OpenAPI 3.1, generated from the catalog. One path per fixture, each a GET returning `application/pdf`. The endpoint's `summary` is the fixture's description; tags carry the facet values for tooling that groups by tag.

```yaml
openapi: 3.1.0
info:
  title: pdfbin.net
  version: "1.0.0"
  description: Free CC0 PDF fixtures at stable flat URLs
  license: { name: CC0-1.0, identifier: CC0-1.0 }
servers: [{ url: https://pdfbin.net }]
paths:
  /fax-cover-letter-scanned-noisy.pdf:
    get:
      summary: Fax cover sheet on US Letter, rendered as a noisy 300 DPI scan
      tags: [document-shape:fax-cover-sheet, provenance:scanned-noisy]
      responses:
        "200":
          description: PDF fixture (CC0)
          content: { application/pdf: { schema: { type: string, format: binary } } }
  # ... one entry per fixture
```

## Library and tooling stack

Python pipeline, no Java.

- **pikepdf** (qpdf C binding) - read/write/encrypt workhorse. Handles AES-256, AES-128, RC4-128, RC4-40 cleanly.
- **reportlab** - generate fresh clean PDFs, document-shape PDFs (fax cover, invoice layouts), and size-targeted fillers.
- **Ghostscript** shell-out with `-dPDFA -dPDFACompatibilityPolicy=1` (strict mode: abort on non-conformance, do not silently degrade) - PDF/A generation. We trust Ghostscript's strict-mode output; no separate validator runs in CI.
- **img2pdf** - assemble scanned-image PDFs.
- **Pillow** - synthesize the scan images (noise, skew, dpi variants).
- **pypdf** - light raw-byte work for the `health` (corrupt) builders (locating xref offsets, trailer boundaries, etc., before mutating).
- **pydantic** (or dataclasses + custom validation) - typed facet records in `facets.py`, validated at build time.

System dependencies (installed in the CI Dockerfile):

- `qpdf` (for pikepdf)
- `ghostscript`

Explicitly not used: veraPDF (Java). The tradeoff is no in-CI PDF/A validation; PDF/A fixtures are only as conformant as Ghostscript's strict mode produces. Catalog records for each PDF/A fixture include `"validation": "ghostscript-strict, no veraPDF cross-check"`. Consumers wanting harder verification can run veraPDF locally against the published bytes; the project doesn't put JVM in its build.

## Generation pipeline

`generate/pipeline.py` is the single entry point:

```python
from facets import validate_facet_record
from builders import health, access, spec, form_factor, size, features, provenance, documents
from catalog import emit_catalog, emit_llms_txt, emit_openapi

manifests = []
for module in [health, access, spec, form_factor, size, features, provenance, documents]:
    for fixture in module.build_all():
        validate_facet_record(fixture)   # raises on unknown facet values
        manifests.append(fixture)

emit_catalog(manifests)    # static/catalog.json
emit_llms_txt(manifests)   # static/llms.txt
emit_openapi(manifests)    # static/openapi.json
```

Each builder is a pure function. Input is one or more files in `generate/sources/`. Output is a written PDF in `static/` plus a returned facet record. The catalog emitter aggregates the records.

`facets.py` is the single source of truth for the controlled vocabularies. Builders import enum values from it; the validator rejects any record that uses an unrecognized value. Adding a new axis or value requires editing `facets.py` deliberately - which makes the schema_version bump a visible change in PR review.

CI is a GitHub Action that:

1. Builds a Docker image with `qpdf`, `ghostscript`, and the Python deps.
2. Runs `python generate/pipeline.py`.
3. Runs `git diff --exit-code static/`. If anything changed, the action fails - forcing the contributor to regenerate locally and commit.

This is how `static/` stays a true snapshot of `generate/` without the build needing to push anything back into the repo.

## Hosting and deployment

GitHub Pages, family two-branch flow:

- `dev` is the default branch. All work happens here.
- Pushing to `production` triggers the Pages workflow, which builds with Hugo and deploys.
- Caddy serves the local `public/` build at `https://pdfbin.example.dev` for dev previews.

Tradeoff accepted: GH Pages enforces a 100MB per-file ceiling, a ~1GB repo size ceiling, and 100GB/month bandwidth. Hence size-variants cap at 50MB per file (with headroom). If pdfbin becomes popular enough to threaten the bandwidth ceiling, the migration target is Cloudflare Pages + R2; that migration is explicitly out of scope for v1.

`CLAUDE.md` will codify the family working rules: commit and push after every change; do not run `hugo server`; use one-shot `hugo --minify` and Caddy for previews.

facet metadata so the same fixture can be discovered along multiple axes.

Engineers who already know what httpbin or placehold.co are. Tone is

## Prior art (research summary)

Findings from research that informed this design:

- **Bin family** (httpbin, webhook.site, pastebin, hastebin, mockbin): splits between *ephemeral capture* (webhook.site, RequestBin - random IDs, user-generated) and *curated catalog* (httpbin, hastebin - stable pronounceable paths, single-tenant). pdfbin sits firmly in the curated half.
- **Placeholder/fixture family** (picsum.photos, placehold.co, jsonplaceholder, fakerapi, robohash): path-based identity, query strings reserved for orthogonal modifiers. Lorem Picsum's `/v2/list` machine index is the discoverability gold standard - and nobody else in the family ships one. via.placeholder.com died in March 2026 when the domain was sold; the longevity story is part of the product. Sites that omit licensing create real CI adoption friction.
- **PDF prior art:** samplefile.com is the meaningful incumbent (21 curated fixtures, JSON manifest with SHA256s) but lacks explicit CC0, immutable URLs, document-shape fixtures, and a corruption taxonomy. ArturT/Test-PDF-Files is the closest "casual CI fixture" set - 3 files, abandoned at 3 commits. py-pdf/sample-files, mozilla/pdf.js, and veraPDF/veraPDF-corpus are each excellent in their niche but none positioned as a general developer-facing fixture host with stable URLs and CC0 licensing.

The unique slot for pdfbin.net is the combination: CC0 + flat immutable URLs + corruption taxonomy + document-shape fixtures + typed multi-axis catalog. Without all five, this would be a samplefile.com clone.
